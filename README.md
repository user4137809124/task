# aqa-tests

Автотесты для `internal-0.0.1-SNAPSHOT.jar`. Описание задания лежит в [TASK.md](TASK.md).

Java 17, JUnit 5, REST Assured, WireMock, Allure, Maven.

## Запуск

Сначала поднять приложение:

```
java -jar -Dsecret=qazWSXedc -Dmock=http://localhost:8888/ internal-0.0.1-SNAPSHOT.jar
```

Порт 8888 должен быть свободен, на нем тесты сами запускают WireMock вместо внешнего сервиса.

Потом:

```
mvn clean test
mvn allure:serve
```

Адрес приложения, ключ и порт мока можно поменять через `-Dapp.url`, `-Dapp.api.key`, `-Dmock.port`.

## Отчет

В Allure тесты разложены по разделам (вход, действие, выход, ключ, валидация, HTTP).
У каждого теста есть шаги, а запросы и ответы приложены к шагам.
На вкладке Categories упавшие тесты делятся на дефекты приложения и проблемы окружения
(например, приложение не запущено).

Каждый тест работает со своим случайным токеном, мок настраивается под этот токен,
так что тесты друг другу не мешают.

Шаги "Ждем ..." - это проверки. Если такой шаг красный, значит приложение повело себя
не так, как ждали, а что пришло на самом деле, написано в сообщении об ошибке.

Что значат коды в отчете: 200 - все хорошо, 400 - неправильный токен или действие,
401 - нет ключа или он неверный, 409 - пользователь уже вошел, 500 и 503 - сервер сломался
или недоступен. 302 - это "ответ лежит по другому адресу", а не успех. 404, 405 и 415
объяснены в описаниях тестов, где они проверяются.

В тестах на неверные данные внешний сервис заранее настроен отвечать "успехом".
Так видно, что отказ пришел именно из-за неверных данных, а не из-за внешнего сервиса.

## Найденные баги

Сверху самое серьезное.

1. Не проходят токены с буквами G-Z. По заданию токен состоит из A-Z и 0-9, а приложение
   проверяет его регуляркой `^[0-9A-F]{32}$`. Если настоящие токены генерируются из A-Z0-9,
   почти в каждом найдется буква дальше F, то есть войти не сможет почти никто.
2. На ответ 302 от внешнего сервиса приложение реагирует как на успех. Для /auth это значит,
   что пользователя пускают, хотя сервис его не подтвердил. Для /doAction клиент получает OK,
   а действие на самом деле не выполнено.
3. Если внешний сервис ответил ошибкой, клиенту приходит просто `500 Internal Server Error`.
   Что пошло не так, из ответа не понять.
4. GET, запрос на несуществующий адрес и JSON в теле дают 500, хотя должны 405, 404 и 415.
   Ошибка клиента выглядит так, будто упал сервер.
5. В тексте ошибки валидации торчит регулярка, и русский там перемешан с английским.
   Отдельного теста на это нет, но видно в ответе на любой неправильный токен.
